# 기능 테스트 결함 발견 및 수정・보완 보고서

## 1. 개요

- **프로젝트**: AI UI/UX 디자인 아카데미 소개 홈페이지 + 정원 신청 시스템 + 멘토 매칭 시스템
- **테스트 기간**: 2026-07-31 ~ 2026-08-12 (개발과 병행한 지속적 테스트)
- **테스트 대상**: React 프론트엔드 전체 페이지(26개 라우트) + Supabase 백엔드(인증・지원・상담・콜백・커뮤니티・문의・학원 일정 7개 도메인)
- **목적**: 실제 사용 시나리오를 재현해 기능 결함을 발견하고, 원인을 규명해 수정한 뒤 재검증까지 완료하는 것을 원칙으로 함
- **총 발견 결함**: 29건 (수정 완료 29건, 미해결 0건) + 조사 결과 결함이 아닌 것으로 판명된 오탐 6건
  - 결함 ID는 발견 시점 기준으로 D-01~D-30까지 부여했으나, D-26은 조사 결과 별개 결함이 아니라 D-27과 동일한 근본 원인의 증상이었음이 밝혀져 D-27로 통합했다(상세 목록에는 진단 과정 기록을 위해 남겨둠) — 그래서 최종 결함 수는 29건이다.

## 2. 테스트 방법론

| 방법 | 설명 | 적용 시기 |
|---|---|---|
| 정적 코드 리뷰 | `npm run lint`(oxlint) + `npm run build`(vite build)로 문법・타입・번들 오류 사전 차단 | 매 작업 완료 시 항상 |
| 수동 시나리오 재현 | 개발 서버(`localhost:5173`)를 직접 띄워 실제 사용자 흐름을 따라가며 확인 | 프로젝트 초반(브라우저 자동화 도구 도입 전) |
| Playwright 브라우저 자동화 | 헤드리스 크로미움으로 회원가입→지원→상담→게시판 작성 등 실제 클릭・입력 흐름을 재현하고, 콘솔 에러・화면 상태・DOM 값을 자동 검증 | 프로젝트 후반(2026-08-12 전후)부터 핵심 회귀 테스트에 적극 사용 |
| Supabase API 직접 검증 | UI를 거치지 않고 Supabase 클라이언트로 로그인・조회・변경을 직접 호출해, RLS(Row Level Security) 정책과 데이터 영속성을 UI 레이어와 분리해 검증 | 백엔드(DB) 연동 이후 |
| 회귀 테스트 | 기능 수정 후 동일 시나리오를 재실행해 부작용이 없는지 재확인(예: 상태 변경을 반복해도 값이 정확히 유지되는지) | 매 수정 후 |

## 3. 결함 요약 통계

### 3-1. 심각도별
| 심각도 | 기준 | 건수 |
|---|---|---|
| Critical | 핵심 기능이 아예 동작하지 않거나, 데이터 정합성이 깨지거나, 화면 전체가 사용 불가능해짐 | 7건 |
| High | 특정 기능이 잘못 동작하거나 데이터가 유실됨(우회 가능하거나 영향 범위가 제한적) | 5건 |
| Medium | 레이아웃/애니메이션이 깨지거나 어색하지만 기능 자체는 동작함 | 11건 |
| Low | 표시 문구・정렬 등 사소한 시각적 결함 | 6건 |

### 3-2. 영역별
| 영역 | 건수 | 비고 |
|---|---|---|
| 데이터베이스/백엔드(Supabase, RLS) | 6건 | 권한 설정, 데이터 영속성, 세션 처리 |
| 프론트엔드 로직(React 상태 관리) | 7건 | 상태 반영 누락, 계산 오류 |
| 프론트엔드 UI/레이아웃(CSS) | 12건 | 반응형, 정렬, 애니메이션 |
| 콘텐츠/문서 정합성(좌표, 텍스트, 문서) | 4건 | 지도 좌표, 문구 노출, 문서-구현 불일치 |

## 5. 주요 결함 상세 설명

### D-27. 로그인 세션-데이터 조회 레이스 컨디션 (가장 중요한 구조적 결함)

**증상**: "게시물 삭제는 되는데 댓글 수정/삭제가 안 된다"는 사용자 보고로 시작. 재현해보니 방금 작성한 내 댓글은 정상 동작하지만, 관리자 계정으로 다른 사람의 댓글을 열어보면 수정/삭제 버튼 자체가 안 보임.

**조사 과정**:
1. Supabase API를 직접 호출해 관리자 권한으로 RLS(Row Level Security) 정책을 테스트 → 백엔드 권한 설정은 100% 정상 동작 확인.
2. 프론트엔드 코드(`canModify` 함수) 로직도 검토했지만 문제 없음.
3. 디버그 로그를 추가해 실제 `currentUser` 값을 실시간 확인 → 관리자 로그인 정보는 정확했으나, **버튼이 표시되는 시점과 안 되는 시점이 갈림**을 확인.
4. 최종적으로 "관리자가 화면에 들어가는 시점"과 "로그인 세션이 실제로 복원되는 시점" 사이에 미세한 시간차가 있고, 그 사이에 데이터를 딱 한 번만 조회하는 구조라 **그 사이의 조회는 비로그인 상태로 실행되어 빈 데이터를 반환**하고, 이후 세션이 복원돼도 다시 조회할 방법이 없다는 것을 확인.

**영향 범위**: 문의 게시판뿐 아니라 지원・상담・콜백・커뮤니티 총 5개 데이터 영역 전부가 동일한 코드 패턴을 쓰고 있어 잠재적으로 같은 문제를 안고 있었음 — 관리자 대시보드에 로그인 직후 진입하면 통계가 0으로 보이는 등, 사용자가 아직 직접 보고하지 않은 다른 화면에도 영향이 있었을 가능성이 있음.

**조치**: 5개 데이터 영역 모두 로그인 사용자 식별 값이 바뀔 때마다 자동으로 재조회하도록 수정. 이 중 하나는 애초에 로그인 상태를 추적하지도 않고 있어 관련 코드를 새로 추가.

**검증**: Playwright로 "관리자 로그인 → 다른 사용자 댓글 삭제 → 문의 등록 → 새로고침 후 유지 확인 → 관리자 답변 등록" 6단계 시나리오를 자동 재현해 전부 통과 확인.

### D-01. 정원 초과 버그

**증상**: 정원 20명인 과정에 관리자가 대기자를 계속 "합격"으로 승인하면 21명, 22명까지도 확정될 수 있음.

**원인**: 지원 상태를 변경하는 함수가 상태값만 바꿀 뿐, 변경 전 현재 확정 인원과 정원을 비교하는 로직이 없었음.

**조치**: 상태를 "합격"으로 바꾸려는 모든 시도(관리자 개별 변경, 일괄 변경 포함)에서 매번 확정 인원을 다시 계산해 정원 이상이면 차단. 관리자 화면에서도 정원이 찬 과정은 "합격" 옵션 자체를 드롭다운에서 비활성화해 애초에 시도할 수 없게 함.

**검증**: 정원을 채운 뒤 추가로 합격 처리를 시도해 차단되는 것을 재현 테스트로 확인.

### D-15 / D-16. Supabase 권한(RLS) 설정 결함

**증상**: 백엔드 연동 초기, 데이터를 심으려는 모든 시도가 권한 오류로 실패.

**원인**: Supabase의 Row Level Security는 "이미 접근 가능한 테이블 안에서 어떤 행을 볼 수 있는지"만 제어하는 기능인데, 이 프로젝트는 다른 앱과 프로젝트를 공유하기 위해 기본 스키마가 아닌 전용 스키마를 새로 만들면서 그 스키마 자체에 대한 기본 접근 권한(GRANT)이 전혀 없는 상태였음. 또한 정원을 채우기 위한 "계정 없는 더미 지원자" 데이터는 그 어떤 로그인 사용자의 소유도 아니어서, "본인 데이터만 등록 가능"이라는 일반 규칙에 걸려 등록 자체가 거부됨.

**조치**: 스키마 단위 기본 권한 부여 + "주인이 없는(null)" 데이터를 위한 예외 정책을 별도로 추가. 이후 커뮤니티・문의 게시판의 시드 데이터를 이관할 때도 동일한 패턴을 재사용해 같은 문제가 재발하지 않도록 함.

**검증**: 시딩 스크립트 재실행으로 정상 등록 확인.

### D-22. 모바일 여정 그래프 좌표 밀림 버그

**증상**: 모바일 화면에서 진행 단계(STEP) 4개 중 뒤쪽 단계일수록 오른쪽으로 심하게 밀려나 화면 밖으로 잘려 거의 보이지 않음.

**원인**: 이 컴포넌트는 데스크톱에서 곡선 그래프 위 정확한 위치에 배치하기 위해 각 요소에 `left`/`top` 인라인 스타일(퍼센트 값, 최대 95%)을 사용한다. 모바일 전용 레이아웃으로 전환하며 `position: absolute`를 `relative`로 바꿨는데, `position: relative` 역시 `left`/`top` 오프셋을 그대로 적용받는다는 CSS 특성(`static`일 때만 무시됨)을 놓쳐, 마지막 단계는 화면 폭의 95%만큼 오른쪽으로 밀려났음.

**조치**: 모바일 스타일시트에서 `left`/`top`을 `!important`로 명시적으로 0 고정(인라인 스타일은 외부 스타일시트의 `!important`로만 덮어쓸 수 있다는 CSS 우선순위 규칙 활용).

**검증**: 모바일 뷰포트 스크린샷으로 4단계 전부 동일한 위치에서 시작하는 것을 확인.

| 관리자가 상담을 신청해도 관리자 화면에서 안 보임(백엔드 연동 이전 시점) | 코드 로직에는 문제가 없었고, 그 사이 브라우저가 새로고침되며 메모리에만 있던 데이터가 초기화된 것 — 당시엔 아직 실제 DB가 없어 발생한 구조적 한계였으며, 이후 백엔드 연동으로 근본 해결됨 |

## 7. 결론

29건의 결함을 발견해 전부 수정하고 재검증까지 완료했다. 이 중 가장 심각도가 높았던 결함(D-27, 로그인 세션-데이터 조회 레이스 컨디션)은 단일 화면의 문제가 아니라 5개 데이터 영역에 공통으로 적용된 코드 패턴의 구조적 결함이었다는 점에서, **한 번의 버그 리포트를 계기로 코드 전반을 점검해 유사한 잠재적 결함을 함께 제거**한 사례로 볼 수 있다. 초기(2026-07-31)에는 정원 초과・반응형 깨짐처럼 핵심 기능・전체 화면에 영향을 주는 Critical 결함이 주로 발견됐고, 후반(백엔드 연동 이후)에는 데이터 영속성・권한(RLS) 관련 결함의 비중이 높아졌다 — 이는 프로젝트가 "프론트엔드 단독 프로토타입"에서 "실제 백엔드 연동 시스템"으로 전환되는 과정에서 자연스럽게 나타난 흐름이다.

현재 시점 기준으로 알려진 미해결 결함은 없으나, 아래는 구조적으로 남아있는 한계이며 별도 과제로 진행할 수 있다.
- 상태 변경(지원 합/불, 상담 배정 등)의 서버 측 권한(RLS)이 "로그인 회원이면 누구나 가능"으로 단순화되어 있어, 화면(라우트) 단의 역할 제한에 의존하고 있음(데모 목적의 의도된 단순화).
- 공지사항・강사진・후기・포트폴리오・파트너사・FAQ는 관리자가 화면에서 직접 수정할 수 없고 코드 수정이 필요함.
