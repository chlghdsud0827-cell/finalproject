# 기능 테스트 결함 발견 및 수정 보고서

## 들어가며

2026년 7월 31일부터 8월 12일까지, 개발을 진행하면서 동시에 기능 테스트를 계속 병행했다. 처음엔 개발 서버를 직접 띄워놓고 화면을 하나씩 눌러보는 수동 테스트로 시작했고, 프로젝트 후반부에는 Playwright로 회원가입부터 지원, 상담 신청, 게시판 글쓰기까지 실제 사용자 흐름을 자동으로 재현해서 확인하는 방식을 많이 썼다. 백엔드를 Supabase로 옮긴 뒤부터는 화면을 거치지 않고 API를 직접 호출해서 권한(RLS) 설정이나 데이터가 실제로 저장되는지도 따로 검증했다.

이 기간 동안 크고 작은 결함을 총 29건 발견해서 전부 수정했다. 아래에는 그중에서도 기억에 남는, 원인을 찾는 데 시간이 걸렸거나 영향 범위가 컸던 것들을 위주로 정리하고, 자잘한 UI 수정 건들은 뒤쪽에 표로 간단히 모아뒀다.

## 초반에 찾은 핵심 버그 두 가지

**정원 초과 버그** (7/31) — 관리자가 대기자를 계속 "합격" 처리하면 정원이 20명인 과정에 21명, 22명까지 확정될 수 있었다. 상태를 바꾸는 함수가 값만 바꿀 뿐 지금 몇 명이 확정됐는지 확인하는 로직이 아예 없었던 거였다. 상태를 바꾸려는 시점마다 현재 확정 인원을 다시 세서 정원을 넘으면 막도록 가드를 추가하고, 관리자 화면에서도 정원이 찬 과정은 "합격" 옵션 자체를 드롭다운에서 없애버렸다. 정원을 다 채운 다음 한 명 더 합격시켜보는 걸로 막히는지 재확인했다.

**모바일 헤더가 통째로 깨지는 버그** (7/31) — 375px 폭에서 헤더 메뉴가 글자 하나하나 단위로 줄바꿈돼서 상단이 세로로 긴 글자 더미처럼 보였다. 모바일 브레이크포인트가 아예 없었던 데다, 한글은 원래 음절 단위로도 줄바꿈이 되기 때문에 폭이 조금만 부족해도 이런 일이 생긴다. 640px 기준으로 브레이크포인트를 넣고 메뉴 항목은 단어 단위로만 줄바꿈되게 고쳤는데, 사이트 전체 페이지 상단에 영향을 주는 문제라 심각도가 높았다.

## 계속 말썽이었던 여정 그래프

홈 화면 하단의 "지원부터 취업까지" 진행 그래프는 이번 프로젝트에서 가장 많이 손댄 컴포넌트다. 처음엔 각 단계를 개별 `<path>`로 나눠서 호버할 때마다 그 시점 기준으로 딜레이를 계산하는 방식으로 만들었는데, 마우스를 빠르게 이 단계 저 단계로 옮기면 애니메이션이 끊기거나 중간부터 다시 시작하는 문제가 있었다. 이건 여러 구간을 하나로 이어 그리고 실제 곡선 길이를 기준으로 `stroke-dashoffset`만 옮기는 방식으로 바꿔서 해결했다.

모바일 버전으로 넘어오면서는 완전히 다른 종류의 버그가 나왔다. 데스크톱 곡선 좌표를 위해 넣어뒀던 `left`/`top` 인라인 스타일(최대 95%)이 모바일 레이아웃으로 전환한 뒤에도 그대로 남아있었는데, `position: relative`도 `absolute`처럼 이 오프셋을 그대로 적용받는다는 걸 놓쳐서 뒤쪽 단계일수록 화면 오른쪽으로 심하게 밀려나 거의 다 잘려나가는 상태였다. 모바일 스타일시트에서 `left: 0 !important`로 명시적으로 고정해서 해결했다.

그다음엔 모바일 자동 재생 애니메이션에서 도입선과 첫 단계 색상이 같은 조건으로 동시에 트리거돼 "이어지는" 게 아니라 "겹쳐서" 채워지는 문제가 또 나왔고, 그걸 고친 뒤에도 "선이 자연스럽게 안 이어진다"는 피드백을 받았다. 원인을 파보니 각 구간의 선을 `padding`/`margin` 수치로 근사해서 흉내내던 방식 자체가 구조적으로 이음매가 어긋날 수밖에 없는 구조였다. 결국 각 단계 박스의 실제 화면 좌표를 `getBoundingClientRect`로 측정해서, 세그먼트별 근사치가 아니라 진짜 좌표 하나로 이어진 단일 연속선을 그리는 방식으로 다시 만들었다. 같은 컴포넌트에서 성격이 다른 버그가 네 번 연속으로 나온 셈인데, 매번 스크린샷과 좌표값을 직접 찍어서 확인한 뒤에야 수정했다.

## 백엔드로 옮기면서 만난 문제들

Supabase로 데이터를 옮기는 과정에서는 권한 설정 관련 버그가 많았다.

처음 시딩 스크립트를 돌렸을 때 `permission denied for schema academy`부터 마주쳤다. 이 프로젝트는 다른 앱과 Supabase 프로젝트를 같이 쓰기 때문에 기본 `public` 스키마 대신 전용 스키마를 새로 만들었는데, RLS(Row Level Security)는 "어떤 행을 볼 수 있는지"만 걸러줄 뿐이고 그 이전에 스키마 자체에 대한 기본 접근 권한(GRANT)이 따로 필요하다는 걸 몰랐다. 스키마 단위 권한을 부여하는 마이그레이션을 추가해서 해결했다.

그다음엔 정원을 채우기 위한 "계정 없는 더미 지원자"를 등록하려는데 RLS 정책 위반으로 막혔다. INSERT 정책이 "본인 명의로만" 등록 가능하게 돼 있었는데, 더미 데이터는 애초에 주인이 없으니 이 조건을 만족할 수 없었던 것이다. `user_id is null`인 경우를 따로 허용하는 정책을 추가했고, 이 패턴은 나중에 커뮤니티・문의 게시판 시드 데이터를 옮길 때도 그대로 재사용했다.

계정을 실제 Supabase Auth로 전환하는 과정에서는, 테스트 계정 하나(이유나)의 합격・멘토 배정 이력이 마이페이지에서 갑자기 안 보이는 일도 있었다. 계정이 새 UUID를 발급받으면서 예전 mock id로 심어뒀던 시드 데이터와 연결이 끊어진 거였다 — 실제로 로그인해서 새 id를 확인한 뒤 관련 데이터를 다시 연결해줬다.

## 게시판 글이 자꾸 사라지는 문제

커뮤니티와 문의 게시판은 한동안 Supabase 연동 없이 브라우저 메모리(React state)로만 동작하고 있었다. 그래서 글을 써도 새로고침하면 사라지고, 다른 브라우저 세션(=다른 사용자)에는 아예 보이지 않는 상태였다. 이건 버그라기보다는 아직 안 옮겨진 범위였는데, 각각 전용 테이블과 RLS 정책을 만들고 Context를 Supabase 연동으로 바꾸면서 해결했다. 학원 일정(관리자가 추가/수정하는 모집・수업・행사 일정)도 같은 문제를 갖고 있어서 동일하게 처리했다.

이 작업들을 마친 뒤 "게시물 삭제는 되는데 댓글 수정/삭제가 안 된다"는 보고를 받았는데, 이걸 추적하다가 이번 프로젝트에서 가장 중요한 버그를 찾게 됐다.

처음엔 권한 설정을 의심해서 Supabase API를 직접 호출해 관리자 권한으로 RLS를 테스트해봤는데 100% 정상이었다. 프론트엔드의 권한 체크 함수도 로직상 문제가 없었다. 결국 디버그 로그를 심어서 실시간으로 확인해보니, 버튼이 보일 때와 안 보일 때가 갈리는 게 눈에 띄었다. 원인은 이거였다 — 지원・상담・콜백・문의・커뮤니티, 이 다섯 개 데이터 영역이 전부 "앱이 처음 켜질 때 딱 한 번만" 서버에서 데이터를 가져오고 있었다. 그런데 로그인 세션 복원은 비동기라서, 이 최초 조회가 세션이 복원되기 전에 먼저 실행되면 로그인 회원만 조회 가능하다는 RLS에 막혀 빈 배열을 받게 되고, 그 이후 로그인이 끝나도 다시 조회할 방법이 없어서 빈 상태가 그대로 굳어버리는 구조였다.

한 화면의 버그가 아니라 다섯 개 데이터 영역에 공통으로 깔린 코드 패턴의 문제였다는 게 중요한 지점이다. 관리자가 로그인 직후 들어가면 통계가 전부 0으로 보이는 것처럼, 사용자가 아직 직접 보고하지 않았을 뿐 다른 화면에도 영향을 주고 있었을 가능성이 크다. 다섯 곳 전부 로그인 상태가 바뀔 때마다 자동으로 다시 조회하도록 고쳤고(그중 한 곳은 애초에 로그인 상태 자체를 안 보고 있어서 그 부분도 같이 추가했다), Playwright로 로그인부터 댓글 삭제, 문의 등록, 새로고침, 관리자 답변까지 이어지는 시나리오를 자동으로 돌려 전부 정상 동작하는 걸 확인했다.

## 버그인 줄 알았는데 아니었던 것들

"이상하다" 싶어서 조사까지 들어갔지만, 실제로는 결함이 아니라고 결론 내린 경우도 몇 번 있었다. 확실한 원인을 못 찾은 채로 고치면 오히려 불필요한 코드 변경이 생기기 때문에, 이런 건 재현해서 확인한 다음 코드를 건드리지 않고 넘어갔다.

- 회원가입한 계정이 새로고침하면 사라지는 것 — 백엔드 연동 전 단계에서는 원래 그렇게 설계된 동작이었다.
- 전체 페이지 스크린샷에서 헤더가 두 번 겹쳐 보이는 것 — 실제 DOM에는 헤더가 하나뿐이었고, 스크린샷 캡처 도구가 만든 시각적 착시였다.
- 비회원 콜백 신청이 권한 오류로 막히는 것처럼 보였던 것 — 테스트 스크립트가 등록 후 결과를 즉시 조회하려 한 게 원인이었고, 실제 앱은 조회 없이 등록만 하므로 문제없었다.
- 모바일 여정 그래프 마지막 단계만 색이 안 바뀌는 것처럼 보였던 것 — 색상 전환 애니메이션이 막 시작한 순간을 캡처한 것뿐이었고, 조금 기다리니 정상적으로 바뀌었다.
- 새로 추가한 학원 일정이 안 보이는 것 — `/schedule`이 월별로 넘겨보는 캘린더였는데, 테스트 데이터를 화면에 보이는 달이 아닌 다른 달짜로 등록해서 안 보였을 뿐이었다.

## 마무리

전체적으로 보면 프로젝트 초반에는 정원 초과나 모바일 헤더처럼 핵심 기능・전체 화면에 영향을 주는 무거운 버그가 발견됐고, 백엔드를 Supabase로 옮기기 시작한 뒤로는 권한(RLS) 설정과 데이터 영속성 관련 문제의 비중이 확 늘었다. 이건 프로젝트가 "프론트엔드만 있는 프로토타입"에서 "실제로 데이터가 저장되는 시스템"으로 넘어가는 과정에서 자연스럽게 나타난 흐름이라고 본다.

가장 기억에 남는 건 역시 로그인 세션-데이터 조회 레이스 컨디션이다. 댓글 하나가 안 지워진다는 사소해 보이는 신고로 시작했는데, 파고들어보니 다섯 개 영역에 걸친 공통 구조 문제였다. 하나의 버그 리포트를 계기로 비슷한 문제를 가진 다른 코드까지 같이 점검하고 고칠 수 있었다는 점에서 의미가 있었다고 생각한다.

현재 알려진 미해결 결함은 없다. 다만 아래 두 가지는 버그라기보다 의도적으로 남겨둔 범위라 참고로 적어둔다.
- 지원 합/불, 상담 배정 같은 상태 변경의 서버 측 권한이 "로그인 회원이면 누구나 가능"으로 단순화돼 있고, 실제 역할 제한은 화면(라우트) 단에서만 이뤄진다. 민감한 데이터를 다루지 않는 데모라 의도적으로 단순화한 부분이다.
- 공지사항・강사진・후기・포트폴리오・파트너사・FAQ는 아직 관리자가 화면에서 직접 수정할 수 없고, 내용을 바꾸려면 코드를 고쳐야 한다.
